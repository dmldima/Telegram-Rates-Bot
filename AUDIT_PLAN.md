# План аудиту багів та неефективностей — Telegram Rates Bot

Документ описує обсяг, методологію та конкретні напрямки аудиту коду бота
курсів валют. План побудований після наскрізного читання всіх модулів
(`main.py`, `handlers.py`, `config.py`, `services/currency_service.py`,
`utils/*`). Кожен пункт містить попередньо виявлені кандидати на дефекти,
щоб аудит одразу мав фокус, а не починався «з нуля».

---

## 1. Мета та критерії готовності

**Мета:** знайти й задокументувати (а далі — виправити) функціональні баги,
логічні помилки, ризики безпеки та неефективності продуктивності/ресурсів.

**Definition of Done для аудиту:**
- [ ] Кожен модуль пройдено за чеклистом нижче.
- [ ] Кожна знахідка має: серйозність, файл:рядок, сценарій відтворення, пропозицію фіксу.
- [ ] Критичні та високі баги мають регресійний тест (зараз тестів немає — див. §7).
- [ ] Знахідки згруповано у issues/PR за пріоритетом.

**Шкала серйозності:** `Critical` (втрата коректності курсу / краш) →
`High` (неправильний результат для користувача) → `Medium` (UX/крайні випадки) →
`Low` (стиль, дрібні неефективності).

---

## 2. Методологія

1. **Статичний прохід** — читання за чеклистом (нижче), лінтери (`ruff`/`flake8`),
   перевірка типів (`mypy`), пошук дублікатів ключів/мертвого коду.
2. **Динамічний прохід** — юніт-тести на парсери (`normalize_amount`,
   `parse_date_any`, `validate_pair_text`) з таблицями кейсів; мок HTTP для
   `currency_service`.
3. **Ручне E2E** — `dev_polling.py` проти реального бота, сценарії з §8.
4. **Профілювання/ресурси** — кількість HTTP-сесій, ріст кеша, час відповіді
   для «вихідних» дат (fallback).

---

## 3. Пріоритетні кандидати на баги (виявлені при читанні)

### 3.1 Коректність курсів та конвертації — `services/currency_service.py`
- **[High] Backup API майже завжди не спрацьовує.** `_try_exchangerate_api_backup`
  працює лише коли `requested_date == today` (рядок ~102). Для будь-якої
  історичної дати резервного джерела фактично немає. Оцінити доцільність або
  розширити.
- **[Medium] `FIXER_API_URL`, `ECB_API_URL`, `FRANKFURTER_BACKUP_URL`,
  `NBU_BACKUP_URL` оголошені, але ніде не використовуються** (`config.py`).
  Мертва конфігурація → або підключити як реальний fallback, або прибрати.
- **[Medium] Інверсія курсу для `UAH/XXX`** (`rate = 1.0 / uah_per_target`).
  Перевірити округлення й відображення `1 UAH = ...` на дуже малих значеннях
  (`{rate:.6f}` може давати `0.000000`).
- **[Medium] Fallback по датах — до 7 послідовних HTTP-запитів**, кожен із
  ретраями (`MAX_RETRIES`). Для «глухої» дати найгірший випадок ~21 запит
  послідовно × timeout. Див. §4 (неефективність).
- **[Low] Широкі `except Exception`** у `get_major_rate`/`get_uah_rate`
  ковтають помилки й повертають `None` — важко відрізнити «немає даних» від
  «збій парсингу».

### 3.2 Логіка розбору повідомлення — `handlers.py`
- **[High] Заплутана й крихка детекція «сума + дата»** (рядки ~141-144).
  `parts[0].replace(',', '').replace(' ', '').replace('.', '', 1)` — заміна
  пробілів беззмістовна (рядок вже розбито `split`), а перевірка
  `first_part.replace('.', '', 1).isdigit() or first_part.replace(',', '', 1).isdigit()`
  надлишкова й дає хибні спрацювання/пропуски для форматів типу `1,000.50 today`.
  Потрібні тести-таблиці й спрощення (делегувати `normalize_amount`).
- **[Low] Мертвий код** `else: rate_result = None` (рядки ~183-184) —
  `rate_result` вже `None`.
- **[Medium] Markdown-ін'єкція/поломка розмітки.** `username = first_name`
  вставляється в `parse_mode="Markdown"` без екранування; символи `_ * [ ]`
  в імені ламають повідомлення або дають несподіване форматування. Розглянути
  `MarkdownV2` з екрануванням або `html`.
- **[Low] `future date` тільки логується** у `parse_date_any`, але хендлер усе
  одно робить запит до API, який поверне «немає даних». UX: краще одразу
  повідомити «дата в майбутньому».

### 3.3 Парсинг чисел та дат — `utils/validation.py`, `utils/date_utils.py`
- **[Medium] «місяць» ≈ 30 днів** (`date_utils.py`, `timedelta(days=amount*30)`) —
  неточність для `N months ago`.
- **[Medium] `normalize_amount` — велика гілкова логіка** без тестів; високий
  ризик крайніх випадків (напр. `1.234.567,89`, `1'000.50`, змішані роздільники).
  Побудувати таблицю очікувань і покрити тестами.
- **[Low] `bare except:`** у `format_date_european` (`handlers.py`) та тихий
  `except ValueError` у `_split_nums` — приховують проблеми.
- **[Low] `normalize_code`** лінійно перебирає всі аліаси з `.lower()` на
  кожній ітерації — коректно, але неефективно; краще нормалізований dict-lookup.

### 3.4 Конфігурація — `config.py`
- **[Medium] Дублікати ключів у `CURRENCY_ALIASES`:** `"eur"` та `"злотий"`
  вказані двічі; є `"PLN": "PLN"` (самопосилання). Тихо перетирається — прибрати
  дублі, додати тест на унікальність.
- **[Medium] Розбіжність між `SUPPORTED_PAIRS` і текстом `/help`.** У help немає
  `EUR/SGD`, `USD/SGD` (хоч вони підтримувані), а `PLN` аліас є, але список пар
  у help/readme треба звірити. Джерело правди — одне.
- **[Low] `USE_REDIS = bool(REDIS_URL)`**, але реальна ініціалізація Redis може
  впасти (ImportError/конект) → fallback у пам'ять. Перевірити узгодженість
  прапорця та фактичного бекенду.

### 3.5 Зберігання стану — `utils/memory_store.py`
- **[High] Непослідовність Redis vs memory.** `set_pair` пише лише в Redis (при
  успіху), `get_pair` читає Redis, при помилці — з пам'яті (де запису немає) →
  «зникла» пара. Визначити стратегію (Redis як єдине джерело + деградація) і
  дуал-райт або чіткий fallback.
- **[Medium] `get_stats`/`delete_pair` викликають `redis.keys("user:*:pair")`**
  — блокуюча O(N) операція на проді; замінити на `SCAN`/лічильник.
- **[Medium] In-memory сховище не має TTL/евікції** — на webhook-інстансі росте
  необмежено (пам'ять), на кількох інстансах — стан не спільний.

### 3.6 Життєвий цикл застосунку — `main.py`, `dev_polling.py`
- **[Medium] Один `aiohttp.ClientSession` на КОЖЕН запит** у
  `_http_json_with_retry` (`async with ClientSession(...)`). Створення/закриття
  сесії на кожен HTTP-виклик — суттєвий оверхед; тримати спільну сесію на час
  життя застосунку й закривати в `on_shutdown`.
- **[Low] `drop_pending_updates=True`** у webhook та polling — свідомо? Втрата
  апдейтів при рестарті.

---

## 4. Неефективності (продуктивність та ресурси)

| # | Місце | Проблема | Пропозиція |
|---|-------|----------|-----------|
| 1 | `currency_service._http_json_with_retry` | Нова `ClientSession` на кожен запит | Спільна сесія, DI/singleton |
| 2 | fallback по датах | До 7×MAX_RETRIES послідовних запитів | Обмежити, паралелити обережно, кешувати «немає даних» |
| 3 | `_rate_cache` | Немає фонової евікції, ключі не спільні між інстансами | TTL-евікція/розмір; за потреби Redis-кеш |
| 4 | `memory_store` redis `keys()` | Блокуюча O(N) | `SCAN`/лічильник |
| 5 | `normalize_code` | O(n) перебір аліасів | dict-lookup за нормалізованим ключем |
| 6 | Синхронний `redis` клієнт в async-коді | Блокує event loop | `redis.asyncio` |

---

## 5. Безпека

- Екранування вводу користувача в Markdown (див. 3.2) — ін'єкція розмітки.
- `BOT_TOKEN`/`REDIS_URL` лише з env — перевірити, що не логуються (греп по логах).
- Немає rate-limiting на користувача → можливий абьюз зовнішніх API з одного
  чату. Розглянути throttling (aiogram middleware).
- Валідація розміру `amount` (дуже великі значення, переповнення форматування).

---

## 6. Порядок робіт (послідовність аудиту)

1. **Інфраструктура тестів** (§7) — без неї фікси неперевірні.
2. **`utils/validation.py` + `utils/date_utils.py`** — таблиці кейсів, фікси парсерів.
3. **`handlers.py`** — детекція «сума+дата», екранування, мертвий код.
4. **`services/currency_service.py`** — сесія, fallback, backup-джерела.
5. **`utils/memory_store.py`** — узгодження Redis/memory, async-клієнт.
6. **`config.py`** — дублі аліасів, звірка пар/довідки.
7. **`main.py`/lifecycle** — спільна сесія, health, shutdown.

---

## 7. Прогалина: відсутність тестів

`tests/` містить лише `__init__.py`. Перед виправленнями створити мінімальний
набір:
- `pytest`, `pytest-asyncio`, `aioresponses`/`respx` для моку HTTP.
- Таблиці для `normalize_amount`, `parse_date_any`, `validate_pair_text`.
- Мок-тести `get_major_rate`/`get_uah_rate` (успіх, fallback, 404, 5xx, timeout).
- Тест унікальності ключів `CURRENCY_ALIASES` та узгодженості `SUPPORTED_PAIRS`↔help.

## 8. E2E сценарії для ручної перевірки

- `/pair EUR/USD` → `21.04.2025` → курс.
- `/pair UAH/USD` → `today` → інверсія коректна.
- Вихідний день → fallback-попередження показано.
- `1 000,50 yesterday`, `1,000.50 today`, `1.234.567,89 2025-01-10`.
- Ім'я користувача зі спецсимволами (`a_b*c`) → розмітка не ламається.
- Майбутня дата → зрозуміле повідомлення.
- Непідтримувана пара → список підтримуваних.
